# F13 — Rotational grazing, finite pasture and manure (isolated candidate)

**Mission:** F13, canonical charter `b8a1e635792b08b0a3d87b987e593a539ac5c123`. **Owner:** Farming. **Engine:** Godot 4.x. **Status:** isolated executable candidate, not integrated into the playable game. Domain `scripts/farm_pasture_rotation.gd`, native runner `scripts/farm_pasture_acceptance.gd`.

## Player experience and domain behavior

Future player interface: inspect three pasture cards showing forage, soil fertility and stored manure; select a paddock and confirm a move, then graze an animal or apply manure to recover depleted land. Actions return explicit player-readable success or denial text. Moving is limited to once per monotonic day; each named animal grazes at most once per day. Winter and storms prevent grazing. Each successful grazing consumes **exactly one forage** and deposits **one manure** in that paddock, subject to bounded storage; no feed, money or animal-care rewards are generated by this optional domain. Manure application consumes two stored units for up to six soil-fertility points, once per paddock per day. Resting fields regrow faster; rain helps and drought slows regrowth. No negative forage, soil or manure.

The default model uses three paddocks with 12/20 forage and 50/100 soil each. State records `last_epoch`, active paddock, last move epoch, season/weather, per-field forage/manure/soil/last amendment epoch, per-animal last grazing epoch, and a cumulative ledger. The calendar is monotonic, with 56-day game years controlled by the Principal. `advance_day` rejects duplicate/skipped days; no annual reset of action identifiers. The state is a **standalone proposal**, not the live `animals.gd` paddock store; the live 7-forage, weekly-rotating paddocks remain unchanged.

## Conservation and restoration

The domain enforces the following independent equations after every transition and on restore:

- `36 + grown - consumed = sum(paddock.forage)`
- `deposited - applied = sum(paddock.manure)`, with `deposited = consumed`
- `150 + soil_gained - soil_lost = sum(paddock.soil)`

All credits record **actual capped increments**, not requested increments. Failed moves, feed attempts, day transitions, and amendments are atomic. `save_state`, `load_state` and `load_json` validate the entire nested snapshot before replacing state, reject non-integral/NaN/out-of-bounds or ledger-inconsistent values, and normalize valid integral JSON floats to integers. This protects accidental corruption, **not** malicious synchronized tampering or forged transaction authorization.

## Dependencies and ownership handoffs

**Principal:** approve new optional `pasture_rotation` save namespace and schema migration; own game-day dispatch, input focus, atomic inventory/animal-care settlement and full assembled-game roundtrip. **F11/F12 Farming:** map actual live animal IDs and welfare/lineage to stable authorized grazing identities; avoid a second source of animal nutrition or compost rewards. **Construction:** approve paddock boundaries and livestock capacity; **Emergence:** supply bounded daily weather/season events; **Village:** optional market/manure delivery tasks. No other lane files, saved games or original assets are modified.

**Integration safety:** existing `animals.gd` already provides three seven-unit weekly rotating paddocks and compost rewards. **Do not** run both systems as independent sources of grazing or manure. Integration requires a single authoritative adapter, data migration with preservation of existing forage and compost, and exact-once settlement receipts; otherwise retain this isolated candidate. An input event must never debit fodder or grant compost twice.

These controls are **not implemented** by this candidate.
